## 1. 交付目标与范围

交付一个可以公开演示的健康测评应用：匿名进入、按步骤填写、服务端保存、刷新恢复、生成评估、查看免费预览、模拟支付、解锁完整报告。以一个人配合 AI、两天约 20 小时有效投入进行倒排。

PDF 标题及提交要求明确为两天，最后两页的三天建议属于文档内部矛盾，采用两天作为计划约束。

## 3. 总体架构与技术栈

采用单仓、单应用、内部按职责分层。前端页面与后端 HTTP 接口同域部署，数据库只有后端能够访问。

~~~mermaid
flowchart LR
    Browser[浏览器：测评与报告] -->|同源 HTTPS + Cookie| Routes[Next.js Route Handlers]
    Routes --> Validation[请求校验与会话鉴权]
    Validation --> Services[测评、报告、模拟支付服务]
    Services --> Domain[纯函数：进度、估算、权限策略]
    Services --> Prisma[Prisma 与事务]
    Prisma --> DB[(PostgreSQL)]
    Tests[Vitest 与 Playwright] --> Routes
    Tests --> Domain
~~~

| 层次 | 选型 | 约束与理由 |
| --- | --- | --- |
| 运行时 | Node.js 22，实施时固定兼容补丁版本 | 本地、CI、生产一致 |
| Web 框架 | Next.js App Router、React、TypeScript | 选择开工时兼容的稳定版本并提交 lockfile；不同时搭 NestJS |
| 样式 | Tailwind CSS + 少量可访问基础组件 | 避免搭建整套后台 UI 框架 |
| 表单与请求 | React Hook Form、Zod、TanStack Query | 表单草稿与服务器状态分开；客户端校验不代替服务端校验 |
| 图表 | Recharts 的一张折线图 | 仅会员挂载真实预测曲线；同时提供文本摘要 |
| 后端 | Node.js Runtime 的 Route Handlers | 不依赖 Edge Runtime；轻量计算同步完成 |
| 数据访问 | Prisma；必要的参数化 SQL | SQL 迁移补充 CHECK、部分唯一索引及事务行锁 |
| 数据库 | Supabase 托管 PostgreSQL | 本地及 CI 使用与部署端兼容的 PostgreSQL 主版本 |
| 测试 | Vitest、Playwright、GitHub Actions | 并发与事务使用真实 PostgreSQL，不用 SQLite 替代 |
| 部署 | Vercel + Supabase | 先验证用户已有账号与区域可达性；账号资源是实施阶段外部前提 |

Route Handlers 使用 app 下的 route.ts 文件；同一路径不能同时放 page.tsx 与 route.ts。因此 /pay 只作为 POST 接口，付费界面位于结果页弹窗。[Next.js 官方说明](https://nextjs.org/docs/app/getting-started/route-handlers)

## 4. 前端设计

### 4.1 页面、路由和数据契约

| 页面/组件 | 路由 | 展示与行为 | 调用接口 |
| --- | --- | --- | --- |
| 开始与继续 | / | 产品说明、预计耗时、数据用途；有会话则展示继续测评/查看报告 | GET /api/v1/session；POST /api/v1/sessions |
| 基本信息 | /assessment/profile | 年龄、生理性别、未预选的健康数据同意与模型适用范围确认 | PUT /api/v1/assessments/:id/steps/profile |
| 目标 | /assessment/goal | 减重、维持、增重三个卡片，保存成功后给一段对应说明 | PUT .../steps/goal |
| 身体数据 | /assessment/metrics | 身高、当前体重、目标体重；固定 cm/kg，支持一位小数 | PUT .../steps/metrics |
| 运动频率 | /assessment/activity | 0 次、1–2 次、3–5 次、6–7 次/周 | PUT .../steps/activity |
| 确认 | /assessment/review | 已填摘要、编辑入口、生成报告；不展示服务端内部计算过程 | GET /api/v1/assessments/:id；POST .../:id/submit |
| 报告 | /results/:assessmentId | 免费摘要或会员报告、重新测评入口 | GET .../:id/result |
| 解锁弹窗 | 结果页内 Dialog | 显示解锁权益和“模拟支付，不扣款”；成功后重新读取结果 | POST /pay |
| 合成演示 | /demo | 明示固定合成数据，可比较免费/完整视图；返回个人测评不切换身份 | GET /api/v1/demo/paid?view=preview 或 full |
| 数据用途与删除 | /privacy | 保存用途、期限、匿名恢复限制；二次确认后删除本人全部演示环境数据 | DELETE /api/v1/me |

采用四个数据步骤，章节进度为 0/25/50/75/100%，确认页不计入数据步数。加载反馈在 submit 请求期间展示；接口完成立即展示结果，不伪造长时间计算。

首页不重复询问年龄段；profile 直接填写精确年龄，减少一次重复输入。两处个性化反馈分别为目标保存成功后的说明，以及提交成功后根据真实结果生成的报告引导。

### 4.2 表单 Schema

| stepKey | 完整替换的本步骤字段 | 交互 |
| --- | --- | --- |
| profile | age、sex、healthDataConsent、consentVersion、modelScopeConfirmed、scopeVersion | 点击下一步；两项确认均不预选；同意前数据仅存在内存 |
| goal | goal | 点选后保存，成功才前进；失败保持当前选择 |
| metrics | heightCm、weightKg、targetWeightKg | 维持目标时目标体重自动等于当前体重，仍在服务端复核 |
| activity | activityLevel | 卡片点击后保存；返回确认页 |

PUT 表示本步骤字段整体替换，并非整个测评对象替换。请求未知字段直接拒绝；不能通过提交 subscriptionStatus、userId、bmi 等字段修改身份或计算结果。

### 4.3 页面状态及异常行为

| 状态 | 界面行为 | 数据规则 |
| --- | --- | --- |
| restoring | 骨架屏，待会话和测评恢复完成 | 不用本地默认值覆盖服务端值 |
| editing | 显示当前表单，可返回 | 未提交的编辑只在内存中 |
| saving | 按钮禁用、显示“正在保存” | 同一页面只允许一个保存请求 |
| saved | 显示“已保存”，导航到后续步骤 | 只使用服务端返回的 revision/progress |
| save_failed | 错误提示、保留输入、原请求重试 | 网络超时重用原 Idempotency-Key 和原请求体 |
| validation_error | 字段下方提示并聚焦首个错误 | 不更改服务端数据 |
| revision_conflict | 提示其他标签页已更新；获取最新内容供重新编辑 | 不自动覆盖，不盲目合并旧数据 |
| session_expired | 提示会话失效，回首页重新开始 | 本期没有找回账号功能，不能仅凭 sessionId 恢复 |
| submitting | 显示生成状态，禁止重复修改 | 重试保持相同请求标识 |
| model_unsupported | 展示不适用原因、修正误填/返回目标/结束测评入口；无付费按钮 | 不显示内部异常热量，不承诺必须改出一份计划 |
| report_load_failed | 保留非敏感页面结构，显示重试入口 | 不把请求失败当作未付费，不使用其他身份的缓存 |
| pay_pending | 支付按钮禁用，提示正在解锁 | 保留原 eventId、请求键与请求体 |
| pay_unknown | 请求超时/断网时提示“结果待确认” | 先 GET session/result 对账，再原键重试；不宣称支付失败，也不生成新事件 |
| pay_succeeded | 主动失效结果查询并重新请求 | 不用客户端布尔值宣告已解锁 |
| feature_disabled | 隐藏模拟支付/演示入口并说明环境限制 | 以后端功能开关为准，不尝试绕过禁用端点 |

刷新恢复入口先 GET session，再按 assessmentId 获取草稿。未完成时进入第一项字段校验未通过的步骤；全部完整且 eligibility=SUPPORTED 时进入 review；UNSUPPORTED 时进入当前流程内的不适用提示，不能无限跳回表单；已完成时进入 result。用户主动回到已完成步骤编辑，仅影响当前页面视图；刷新仍按服务端有效进度恢复。

服务端完成的步骤有持久化保证，尚未点击保存的输入不承诺恢复。为避免漏保存，单选自动保存；输入型步骤在下一步保存，不在每次键盘输入时写库。

普通 TanStack Query 键使用 sessionId 与 assessmentId；演示键独立使用 public-demo、view，不覆盖普通身份缓存。新建普通身份或删除数据时取消旧身份在途请求并清空对应缓存。令牌不放 localStorage，不放 URL。重新聚焦报告页时重新校验权益，页面挂起后恢复也重新请求结果。

支付超时的待确认信息可在 sessionStorage 仅保存 sessionId、assessmentId、eventId、请求键和套餐，不保存令牌、身体数据；恢复页面先对账，成功确认后清除。切换普通身份时不得复用旧待确认请求。应用展示“解锁成功”前必须完成 session 与 result 的重新读取，确认新 Cookie 已由服务端发出。

## 5. 后端模块及职责

| 模块 | 主要职责 | 不应承担的工作 |
| --- | --- | --- |
| SessionService | 创建匿名用户与会话；解析 token；验证过期与撤销 | 不接受客户端指定用户身份 |
| AssessmentService | 新草稿、步骤保存、完整性校验、revision、提交事务 | 不把 HTTP request 直接传给 ORM |
| ProgressPolicy | 根据合并后答案计算有效完成步骤和下一步 | 不信任浏览器 currentStep |
| HealthCalculator | 从完整输入和固定时间产生确定性结果 | 不读数据库、网络、环境变量和系统时间 |
| EligibilityPolicy | 适用范围、目标可行区间、输出支持范围；返回原因码 | 不把筛选通过解释成医学认证 |
| ResultService | 读取已完成结果，按当前订阅投影成不同 DTO | 不返回 Prisma 模型或完整内部快照 |
| SubscriptionPolicy | 按订阅状态和到期时间判断有效权益 | 不信任 Cookie 中的会员标志 |
| MockPaymentService | /pay 校验、支付事件去重、原子激活订阅 | 不模拟真实支付签名验证或收款凭证 |
| IdempotencyService | 请求键、请求哈希、成功响应回放 | 不用进程内 Map 承担多实例一致性 |
| 数据访问层 | Prisma 查询、事务、必要行锁 | 不在 UI 直接调用 |

处理顺序：请求大小/JSON 检查 → 同源校验 → 会话解析 → Schema 校验 → 资源归属检查 → 幂等与事务 → 业务结果投影 → 标准响应与脱敏日志。

## 6. 会话、权限和响应约定

### 6.1 身份识别

- userId 标识匿名用户；sessionId 标识一次可撤销会话；二者均不是访问凭证。
- sessionToken 为加密安全随机生成的 32 字节 base64url 字符串；数据库只存 SHA-256 哈希。
- 浏览器 Cookie 名称 health_session，生产设置 HttpOnly、Secure、SameSite=Lax、Path=/，不设置父域共享；设置 Expires 与数据库 expires_at 一致，Max-Age 为剩余有效秒数，支持关闭浏览器后恢复，不因普通读取自动续期。
- 普通未支付会话初始 7 天有效，以数据库 expires_at 为准。首次激活或新一期支付在同一事务中将当前会话 expires_at 更新为 max(原期限, subscription.expires_at + 7 天)，不更换 token；这 7 天也用于到期后再次模拟激活。权益有效期间的新事件只同步至该固定期限，不按请求时间滚动续期。
- 支付成功、原请求回放以及 GET session 均以数据库当前期限重新设置 Cookie，Cookie 不进入历史回执；GET session 只同步客户端有效期，不延长数据库期限。curl 在支付与恢复会话时同时使用 -b/-c 保存新 Cookie。响应丢失后必须执行前端待确认对账；若 Cookie 在对账前已经丢失/过期，本期仍不提供凭空找回，README 明示这个匿名身份限制。
- 删除 Cookie 或更换设备不能恢复匿名身份；这与正常已确认支付后至少覆盖完整会员期的保证分开说明。
- HTTP 客户端可使用 Authorization: Bearer <session-token>；浏览器只使用 Cookie。两者同时出现且不一致时返回 401，不悄悄选择身份。
- 所有私人资源查询必须带 user_id 条件；知道其他人的 UUID 也不能读取，越权返回 404。
- POST /sessions 在已有有效普通用户凭证时返回现有会话及当前测评；无有效会话时，在用户选择重新开始后创建新匿名用户。前端串行发起，避免组件挂载自动重复创建。
- /demo 只调用固定合成数据的公开只读端点；不创建会话，不写 Set-Cookie，不清除或替换 health_session。返回普通测评直接读取原会话。不得把“新标签页”当作会话隔离方式，也不开放任意 sessionId 访问入口。
- 无 Cookie 的首次创建请求如果响应丢失，可能产生一条孤立匿名草稿；本期接受该限制，清理时按保留策略处理，不宣称创建接口具有跨无身份请求的恰好一次语义。

### 6.2 请求与响应

API 使用 camelCase，数据库使用 snake_case；时间戳采用 ISO 8601 UTC，预测日期使用 YYYY-MM-DD，并标明以 UTC 自然日计算。用户输入统一 cm、kg，热量单位 kcal/day。

成功响应：

~~~json
{
  "data": {
    "assessmentId": "<assessment-id>",
    "revision": 2
  },
  "meta": { "requestId": "<request-id>" }
}
~~~

错误响应：

~~~json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请检查填写内容",
    "fields": { "heightCm": "身高超出本演示支持的范围" }
  },
  "meta": { "requestId": "<request-id>" }
}
~~~

| HTTP | 错误码 | 行为 |
| --- | --- | --- |
| 400 | INVALID_JSON | 非法 JSON，含 JSON 不支持的 NaN/Infinity 字面量 |
| 401 | SESSION_REQUIRED / SESSION_EXPIRED | 缺少、伪造、过期或撤销凭证 |
| 403 | ORIGIN_REJECTED / READONLY_DEMO | Cookie 写请求来源错误，或修改只读示例 |
| 404 | ASSESSMENT_NOT_FOUND | 资源不存在或归属他人 |
| 404 | FEATURE_DISABLED | 模拟支付/公开演示开关关闭，端点无写入 |
| 409 | STEP_OUT_OF_ORDER / REVISION_CONFLICT | 跳步、旧版本；错误 details 附 nextStep 或 currentRevision |
| 409 | ASSESSMENT_FINALIZED / RESULT_NOT_READY | 修改已完成测评或提前读取结果/支付 |
| 409 | IDEMPOTENCY_KEY_REUSED / PAYMENT_EVENT_REUSED | 同一个请求/事件标识被用于不同内容 |
| 413 | PAYLOAD_TOO_LARGE | JSON 请求体超过 16KB |
| 422 | VALIDATION_ERROR / CONSENT_REQUIRED / INCOMPLETE_ASSESSMENT | 类型、数值、跨字段、同意或完整性问题 |

### 7.4 提交与结果

### 7.5 模拟支付

POST /pay：

~~~json
{
  "assessmentId": "<assessment-id>",
  "eventId": "<uuid>",
  "planCode": "DEMO_30D"
}
~~~

当前版本所有支付均为模拟：按钮与响应注明 simulated=true，不收集卡号，不发起第三方扣款。该端点是题目要求的模拟成功事件入口，不能称为已实现真实第三方 webhook 验签。

服务端根据会话确定用户，检查 assessment 属于此用户且已完成；planCode 只能为服务器已知常量，客户端不能指定金额、有效期或会员状态。

首次支付创建 outcome=ACTIVATED 的已处理事件，设置订阅有效期为服务器当前时刻 + 30 天。会员有效期间新 eventId 返回 ALREADY_ACTIVE，并插入 outcome=ALREADY_ACTIVE 的已处理事件，明确没有再次激活；不增加会员时长。同一 eventId 无论更换请求键与否，均回放其首次处理结果。到期后只有从未处理过的新 eventId 才能开启新一期。

支付事务依次检查请求回执、相同 eventId 的任何已处理事件、当前权益；不能先因已到期而跳过旧事件去重。结构/套餐校验通过后，同 eventId 不同 assessmentId 或有效 planCode 返回 PAYMENT_EVENT_REUSED；本期只有 DEMO_30D，未知套餐在参数校验阶段返回 422，不与事件冲突码混用。新请求键重放旧事件时，仅新增该键回执，不新增事件或延长期限；响应同时标记 Payment-Event-Replayed: true。

首次处理事件时，同一事务更新当前会话的权益覆盖期限、users.purge_after 和请求回执；任何一项失败全部回滚。重放不再次延长这些期限，仅在响应阶段按数据库当前会话期限补发 Cookie。未来多会话登录不在本期范围内，本期保证的是完成支付的当前会话。

首次激活的安全响应 data 示例：

~~~json
{
  "paymentId": "<payment-id>",
  "eventId": "<event-uuid>",
  "outcome": "ACTIVATED",
  "simulated": true,
  "activation": {
    "startsAt": "2026-09-28T00:00:00.000Z",
    "expiresAt": "2026-10-28T00:00:00.000Z"
  }
}
~~~

ALREADY_ACTIVE 时 paymentId 仍为本次已处理事件的非空 ID，outcome 为 ALREADY_ACTIVE，activation 保存处理当时已有订阅的期限快照，并不表示本次发生了激活。两种响应都记录事件与请求回执。回放返回历史处理结果，不承诺回放时权益仍有效；旧 ACTIVATED 或 ALREADY_ACTIVE 事件都不能在到期后重新激活。

支付响应不包含完整报告。前端等待成功或回放后 GET result，当前权益和完整展示一律取决于新查询响应，不能根据历史 outcome 直接设置会员状态。

### 7.6 可重放调用设计

README 的示例在完成测评后执行；通过 cookie jar 携带之前创建的会话，Cookie 写请求必须带与部署地址一致的 Origin。

~~~shell
curl -X POST '<base-url>/api/v1/sessions' \
  -H 'Origin: <base-url>' -H 'Content-Type: application/json' \
  -c '<cookie-jar-file>' -d '{}'

# 按 README 顺序保存四步并提交，使用响应中的 assessmentId/revision。
curl -X POST '<base-url>/pay' \
  -H 'Origin: <base-url>' -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: <payment-request-uuid>' \
  -b '<cookie-jar-file>' -c '<cookie-jar-file>' \
  -d '{"assessmentId":"<assessment-id>","eventId":"<event-uuid>","planCode":"DEMO_30D"}'

curl '<base-url>/api/v1/assessments/<assessment-id>/result' \
  -b '<cookie-jar-file>'
~~~

重复第二条请求时保持 body 与 Idempotency-Key 完全相同。所有占位符在最终交付 README 中说明来源，线上实际 sessionId 为合成示例 ID，不能当作登录令牌。

### 7.7 响应契约冻结与异常分支

开工第一阶段先将以下契约落成 Zod/TypeScript 与 OpenAPI，再实现页面；不是第二天补文档时才决定字段。所有业务成功响应使用 data/meta 包装，health/ready 和 DELETE 204 除外。

| 对象/接口 | 必须定义的字段与语义 |
| --- | --- |
| SessionDto（GET session、POST sessions） | sessionId、expiresAt、currentAssessmentId、nextStep、consent、subscription、capabilities；currentAssessmentId 与 nextStep 无对象时为 null |
| consent | requiredVersion:string、acceptedVersion:string\|null、acceptedAt:UTC时间\|null、accepted:boolean |
| subscription | effectiveStatus=INACTIVE/ACTIVE/EXPIRED；startsAt/expiresAt 为时间或 null，INACTIVE 均为 null；有效期边界使用一次固定 now 判定 |
| capabilities | mockPaymentsEnabled:boolean、publicDemoEnabled:boolean；环境能力不是鉴权依据，后端独立校验 |
| AssessmentDto（GET by-id/current、新建草稿） | assessmentId、status、revision、sourceAssessmentId、answers、scope、progress、eligibility；current 选最新创建测评，存在草稿时就是该草稿 |
| answers | age/sex/goal/heightCm/weightKg/targetWeightKg/activityLevel，未填写统一 null；不得含 userId、同意时间、计算结果或 ORM 关系 |
| scope | requiredVersion、acceptedVersion、confirmedAt、confirmed，供表单恢复；复制旧答案不复制适用范围确认 |
| progress | completedSteps、invalidatedSteps、percent、nextStep、canSubmit；nextStep 仅为四个 stepKey 或 null，完整时为 null，页面再决定 review/不适用/result |
| eligibility | status=INCOMPLETE/SUPPORTED/UNSUPPORTED、reasonCodes:string[]；只返回白名单原因，不返回未解锁计算值 |
| StepSaveDto | assessmentId、status、revision、savedStep、answers（仅本步骤公开答案）、progress、eligibility；profile 保存后另带最新 consent/scope |
| SubmitDto | assessmentId、resultId、status=COMPLETED、revision；无 nutrition/prediction |
| ReportDto | 以 access=PREVIEW/FULL 为判别联合；两类均有 summary、warnings、subscription、paymentAvailable、upgradeRequired、notice；FULL 才有 nutrition、prediction、algorithmVersion |
| warning | code、message；warnings 始终为数组，无提示是 [] 而不是 null/省略；HORIZON_EXCEEDED 在付款前披露无日期预测，但不泄漏具体预测值 |
| PaymentDto | paymentId、eventId、outcome=ACTIVATED/ALREADY_ACTIVE、simulated=true、activation:{startsAt,expiresAt}；两个 ID 均非空；均为历史处理回执 |
| DemoDto | mode=DEMO、sessionId、assessmentId、view、report；定位 ID 仅来自服务端配置；两种视图的 paymentAvailable 均 false，演示 UI 不提供支付 |
| ErrorDto | error:{code,message,fields?,details?}、meta.requestId；details 仅白名单 nextStep/currentRevision/reasonCodes/allowedTargetRange；不回显请求体或内部异常 |

新测评 POST：copyFromAssessmentId 只接受本人 COMPLETED 测评；已有 DRAFT 则 200 返回现有草稿，不覆写；否则 201 创建。复制时重置 scope 确认字段，因此返回 profile 重新确认。新建、查询与恢复使用同一 AssessmentDto。

数值契约：数据库 numeric 经显式转换返回有限 JSON number，不输出 ORM Decimal 对象或数字字符串；日期显式格式化。BMI 展示从快照原始输入按同版定义一次舍入到一位，避免三位持久化值再次舍入造成双重舍入。热量只在最终结果处舍入一次，日期不经过本地时区解释。

功能开关按默认关闭、失败时拒绝提供能力的方式处理：MOCK_PAYMENTS_ENABLED=false 时 POST /pay 返回 404 FEATURE_DISABLED，任何事件/权益/回执均不写；DEMO_MODE=false 时公开 demo 返回相同错误，不读取固定数据。普通已存在且有效的权益读取不受模拟支付开关影响。开关检查优先于幂等回放，停用后不继续受理模拟调用。

典型模型拒绝响应（不含原始 599 等异常输出）：

## 8. 状态、顺序、重复和并发语义

### 8.1 测评与订阅状态分开

测评持久化状态只有 DRAFT 和 COMPLETED。READY 是“字段完整且 eligibility=SUPPORTED”的派生条件；UNSUPPORTED 是模型判断结果而非第三种持久化测评状态。SUBMITTING 仅为 UI 状态，事务失败或模型不适用均保持 DRAFT，不留下卡住的任务。

~~~mermaid
stateDiagram-v2
    [*] --> DRAFT
    DRAFT --> DRAFT: 分步保存与修正
    DRAFT --> COMPLETED: 校验、计算、保存结果并提交事务
    COMPLETED --> [*]: 只读快照
~~~

完成后不回改原测评；重新测评创建新的 DRAFT，可复制本人旧答案，但重置 scope 确认并要求重新确认适用范围，旧结果保留。订阅归属于用户而非某次测评，付费期间可查看本人各份报告。历史列表页延后，但数据关系可支持它。

### 8.2 有效进度

步骤顺序固定为 profile → goal → metrics → activity，服务端从保存的答案计算最长连续有效前缀，不持久化另一份容易漂移的 currentStep 或 completedSteps。

允许返回修改任意已开放步骤；首次填写后续步骤时必须具备有效前置步骤。修改 goal 或 profile 后如果现有 metrics 不再满足跨字段规则，保留原值以便用户修改，但在 progress 中标记 metrics 失效，completedSteps 回退到连续有效前缀，submit 被拒绝。后续已输入的 activity 值可以保留；metrics 修正后重新派生有效进度。

例如减重目标 70→65 改成增重，goal 保存成功，但 metrics 被标记需修改，不能把 65kg 当作增重目标提交。单独保存 metrics 时则必须立即通过目标方向和全部约束，否则整个保存拒绝。

完成度只表示字段填写情况，不等于算法可用：activity 保存使字段完整后，服务端运行 EligibilityPolicy，允许 200 保存答案并返回 percent=100、nextStep=null、canSubmit=false、eligibility=UNSUPPORTED。UI 展示明确结束路径；强行 submit 再次判定后返回 422，不生成结果、不允许 /pay。字段不完整时 eligibility=INCOMPLETE；所有条件通过才可提交。

canSubmit 的完整条件为 status=DRAFT 且所有步骤有效且 eligibility=SUPPORTED。COMPLETED 始终 canSubmit=false；其结果按生成时的算法/范围版本读取，不因新规则升级而重新计算历史报告或将其改回草稿。

### 8.3 幂等协议

适用新测评、步骤 PUT、submit 和 /pay。Idempotency-Key 为 UUID，作用域为 (user_id, operation, key)，operation 包含方法、资源 ID 和步骤路径。

请求哈希由校验并规范化后的 JSON 计算，包含 expectedRevision；对象字段排序，不依赖原始 JSON 字段顺序。记录仅保存成功响应的安全 data 部分，排除 token、Cookie、原始计算结果；保留至少整个会话有效期。

| 情况 | 返回与写入 |
| --- | --- |
| 同 key、同语义内容 | 返回原成功 data，设置 Idempotency-Replayed: true，不重复业务写入 |
| 同 key、不同内容 | 409 IDEMPOTENCY_KEY_REUSED |
| 步骤修改使用不同 key、旧 revision | 409 REVISION_CONFLICT，即使新内容看起来相同；submit 的例外见 7.4 |
| 不同 key、当前 revision、值完全相同 | 200，不增加 revision，但记录本次成功回执 |
| 写入已成功、响应丢失 | 原 key 重试恢复响应，避免“其实已保存但前端报冲突” |
| 校验失败或事务回滚 | 不保存成功回执，修正内容后使用新 key |

回放可能携带旧 revision，前端遇到 Idempotency-Replayed 必须重新 GET 测评同步最新状态，不能回退覆盖更新后的本地查询缓存。错误 meta.requestId 始终代表本次 HTTP 请求，回放不伪装成新业务写入。

### 8.4 数据库事务边界

同一匿名用户写操作量很小，统一在短事务内锁定 users 行，以简化测评、同意、支付和回执之间的串行一致性；同时使用客户端 expectedRevision 防止陈旧编辑覆盖。数据库行锁不能代替 revision：它只解决执行顺序，无法判断用户编辑时看到的版本。

统一事务流程：

1. 校验会话、参数格式与资源归属。
2. 开启 READ COMMITTED 事务，以参数化 SELECT ... FOR UPDATE 锁当前 users 行；进入后复核会话有效性、所有权与只读身份，不因已完成状态提前拒绝历史回放。
3. 查询本 operation/key 的回执，若相同则回放；冲突则拒绝。
4. 重读测评或订阅；比较 expectedRevision，检查顺序、完整性或权益条件。
5. 完成业务写入；测评实际发生改变时 revision 加一。
6. 在同一事务写入幂等成功回执；事务提交后响应。

Submit 的结果插入、测评 COMPLETED 和回执必须同事务。/pay 的事件处理、订阅变更（如需）、当前会话期限、数据保留期限和回执必须同事务。普通新业务写入也更新数据保留期限；回放不滚动延长。所有写路径锁顺序一致，不在事务里发网络请求、调用第三方或等待 UI。

初始事务参数：lock_timeout=2s、statement_timeout=4s、Prisma 事务 timeout=5s/maxWait=2s；以最终部署实测调整，不能无限等待。锁/事务超时或死锁统一为 503 TEMPORARILY_UNAVAILABLE，重试复用请求键并有界退避；业务 409/422 不自动重试。若提交结果暂时未知，下次相同键先查询回执。数据库时间戳、权益和保留期限在锁取得后使用同一个服务端 now。

~~~mermaid
sequenceDiagram
    participant UI as 浏览器
    participant API as 接口
    participant DB as PostgreSQL
    UI->>API: PUT 步骤 + revision=N + key=A
    API->>DB: 事务：锁用户、查回执、读取 revision
    API->>DB: 写答案与 revision=N+1，写回执
    DB-->>API: 提交成功
    API--xUI: 响应在网络中丢失
    UI->>API: 同一请求 key=A 重试
    API->>DB: 查已提交回执
    API-->>UI: 原成功 data + Replayed
    UI->>API: GET 当前状态，刷新 revision
~~~

## 9. 数据库详细设计

共七张表。核心计算输入采用强类型列，避免全部塞入 JSON 后失去约束；结果曲线与算法快照使用 JSONB。所有 ID 为 UUID，时间戳使用 timestamptz，日期使用 date；本期不引入通用逻辑删除字段。

下列表格除明确写“可空”的列外，一律 NOT NULL；DEFAULT 不替代 NOT NULL。UUID 在服务端生成；created_at 默认 now()，updated_at 创建时初始化、实际业务变更时更新。所有外键 ON UPDATE RESTRICT；ON DELETE 默认 RESTRICT，唯一例外是 assessments 的来源自引用使用 NO ACTION，允许同一用户全部测评在同一 DELETE 语句结束时一起消失。所有 CHECK 的可空分支使用显式 IS NULL/IS NOT NULL，不依赖 SQL NULL 比较结果通过检查。

### 9.4 assessment_results：不可变结果快照

| 字段 | 类型 | 可空/默认 | 说明 |
| --- | --- | --- | --- |

| assessment_id | uuid | 非空唯一外键 | 每次已完成测评最多一份结果 |
| source_revision | integer | 非空 | 计算读取的草稿 revision，完成后的 revision=source_revision+1 |
| algorithm_version | varchar(32) | 非空 | demo-v1.1，升级后旧结果不重算 |
| input_snapshot | jsonb | 非空对象 | 规范化输入，便于复现，绝不直接返回客户端 |
| calculation_metadata | jsonb | 非空对象 | 系数、政策版本、预测情景、适用范围提示 |
| bmi | numeric(6,3) | 非空 | 中间计算不提前截断，持久化保留三位 |
| resting_energy_kcal | integer | 非空 | 静息能量估计，展示整数 |
| maintenance_kcal | integer | 非空 | 维持摄入估计 |
| suggested_intake_kcal | integer | 非空 | 目标摄入估计 |
| prediction_status | varchar(24) | 非空 | PROJECTED / AT_TARGET / HORIZON_EXCEEDED |
| base_date | date | 非空 | UTC 提交日期 |
| target_date | date | 可空 | 超出两年情景窗口时为空 |
| duration_days | integer | 可空 | 非负；超出窗口时为空 |
| weekly_change_kg | numeric(4,2) | 非空 | 减重/增重 0.25；维持 0 |
| prediction_curve | jsonb | 非空数组 | 日期/体重有序节点；至多 106 个 |
| created_at | timestamptz | now() | 生成时间 |

约束：source_revision >=0、bmi >0、resting_energy_kcal/maintenance_kcal >0，suggested_intake_kcal 在 [1000,5000]（仅本版演示输出范围）。prediction_status 限定三种枚举；input_snapshot/calculation_metadata 顶层为对象，prediction_curve 为数组且长度 <=106。JSONB 类型检查使用 CASE 保护后续数组函数，不能指望 AND 的求值顺序。

- PROJECTED：target_date/duration_days 非空，duration_days 在 1–730，target_date=base_date+duration_days，weekly_change_kg=0.25，曲线长度至少 2。

- HORIZON_EXCEEDED：target_date/duration_days 均为空，weekly_change_kg=0.25，曲线为空。
- 节点键、有限数值、日期递增、首尾及体重方向由服务端 Schema/纯函数验证；不适用结果不得插入本表。超长但其余适用的情景仍可完成，免费 warnings 预先披露缺少日期/曲线。

COMPLETED 与恰好一条结果的跨表对应通过提交事务保证并集成测试；不伪称一个普通 CHECK 就能验证跨表存在性。结果写入后应用没有更新入口；重新计算产生新 assessment。

### 9.5 subscriptions：当前访问权益

| 字段 | 类型 | 可空/默认 | 说明 |

| status | varchar(16) | INACTIVE | INACTIVE / ACTIVE |

UNIQUE(user_id, operation, key)、INDEX(created_at)。CHECK response_status 在 200–299、response_data 为 JSON 对象、request_hash 为 64 位十六进制；sessions.token_hash 与 payment_events.request_hash 使用同样格式检查。本期回执跟随整个匿名用户数据清理，不在会话或权益有效期间提前删除；因此清理任务不参与在线幂等判定。

### 9.8 迁移、权限与测试数据

- Prisma Schema 是模型入口，提交生成的 SQL migrations；手工补充的 CHECK/部分索引一并版本管理。
- 开发使用 migrate dev；测试和线上使用 migrate deploy；生产不使用 db push 或启动时 reset。
- 选择专用数据库 schema，避免通过 Supabase 公开 Data API 暴露健康表；运行角色只授予必要表权限，迁移角色独立保存。
- 不在浏览器使用 Supabase service_role 密钥；Cookie/Bearer 认证在 Next.js 服务端完成。
- 数据生命周期与主动撤回按下文固定规则执行，不再笼统承诺“创建后 30 天删除”。清理不得在启动/seed 时自动清空。
- Seed 只向明确标识的演示用户写合成数据，不覆盖普通用户；已支付演示、普通未支付、过期和未完成夹具用于不同验证环境。
- 固定示例 is_demo=true，不允许普通认证、更新、复制、支付或删除；/demo 的只读入口从配置定位示例并保持原普通身份。例行清理排除固定示例，由交付者显式维护到期或移除。

普通数据保留规则：新用户 purge_after=now+30 天；每次产生实际业务变更时，取 max(原 purge_after, now+30 天, 该用户所有未撤销会话 expires_at, 非空 subscription.expires_at+7 天)。新事件即使 ALREADY_ACTIVE 也算已处理业务写入；仅 GET、旧键/旧事件回放不延长保留期。更新与业务同事务，不让期限落后于已承诺权益。

例行清理：维护者每天运行显式清理命令，先 dry-run 展示合成/脱敏 ID 与数量，再按批准范围执行有界批次。仅当 now>=purge_after、无有效会话、无有效权益、is_demo=false 才可清理；取得同一 users 行锁后复核，避免与支付竞争。不配置自动清理任务时，README 必须写明执行责任和实际频率，不能把“可清理”写成已自动删除。

主动撤回：/privacy 提供“删除我的数据并结束测评”，明确同时丢失报告、模拟权益和恢复能力，二次确认后 DELETE /api/v1/me。服务器从当前凭证定位本人，校验确认常量与 Origin，禁止客户端传 userId，禁止删除演示用户；同一用户行锁下依次删除 payment_events、idempotency_records、sessions、assessment_results、该用户全部 assessments、subscriptions、users。关联结果先通过所属测评定位；测评自引用同批删除。任一失败全部回滚。

删除成功返回 204 并清 Cookie；删除请求不保存到即将删除的幂等表。若响应丢失，前端 GET session：401 说明旧身份已失效，清空本地缓存并告知“当前身份不可再访问”，不能仅凭 401 声称数据库删除已证实；有会话则允许重新确认删除。该范围不包含第三方基础设施备份，/privacy 与维护说明须披露备份保留期取决于实际供应商配置，不宣称即时擦除所有备份。

## 10. 服务端算法与输入验证

### 10.1 输入类型和产品范围

以下是请求数据边界，不等于算法适用范围，也不是医学定义；单字段、组合、模型适用性与计算输出分别验证。

| 字段 | 类型和范围 | 非法示例 |
| --- | --- | --- |
| age | JSON integer，18–80 | 缺失、17、81、20.5、"30"、null |
| sex | MALE / FEMALE | 未知字符串；不默认猜测 |
| goal | LOSE_WEIGHT / MAINTAIN / GAIN_WEIGHT | 未知枚举 |
| heightCm | 有限 number，120–220，最多一位小数 | 0、负数、超限、数字字符串、数组 |
| weightKg / targetWeightKg | 有限 number，30–250，最多一位小数 | 0、超限、null、对象、1e309 |
| activityLevel | SEDENTARY / LIGHT / MODERATE / HIGH | 其它字符串或数字 |
| healthDataConsent | 必须 true | false、"true"、缺失 |
| modelScopeConfirmed | 必须 true；scopeVersion=demo-scope-v1 | 未确认或未知版本，不代替用户勾选 |
| expectedRevision | integer >=0 | 字符串、负值、小数 |

Zod strict object，不做宽松数值强转。UI 可将合法输入文本转换为 number，但 API 本身只接受正确 JSON 类型；JSON 解析出非有限数值也必须拒绝。最多一位小数采用小数位验证后再转为规范化十进制，不因浮点乘 10 的误差误拒绝合法输入。

模型范围在 profile 前展示：本演示只为 20–78 岁、非孕期/哺乳期、未被专业人员告知需要个别饮食管理的成年人提供有限情景估算。用户只确认“我已阅读且不属于列出的不适用情况”，不采集具体诊断；不能确认时允许结束，不要求为了继续而勾选。18–19/79–80 的数值类型虽合法，但 profile 返回 PLAN_NOT_SUPPORTED/AGE_OUTSIDE_MODEL_RANGE，不再生成结果后才提醒。20–78 是本版收窄的产品范围，不代表该范围所有人都适用。

跨字段规则与目标可行域（h 为身高米，w 为当前 kg，边界计算使用十进制/整数缩放，避免浮点误差）：

- 当前 BMI 不在 [18.5,40] 时，metrics 返回 PLAN_NOT_SUPPORTED/BODY_OUTSIDE_MODEL_RANGE，不保存本次整步，给出结束/修正误填入口；最终 submit 仍独立复核。
- 减重时目标低于当前；增重时高于当前；维持时必须相等。
- 非维持目标至少相差 0.5kg，最多相差当前体重的 20%；这是单次演示目标限制，并非医学要求。
- 减重取消“目标 BMI <=30”的条件，保留目标 BMI >=18.5；允许从较高体重设定阶段性减重目标。增重保留目标 BMI <=30；维持采用当前模型范围，不增加相互矛盾的目标上限。

~~~text
ceil01(x)  = 向上取到最近的 0.1kg
floor01(x) = 向下取到最近的 0.1kg

减重：L = ceil01(max(30, 0.8*w, 18.5*h*h))
      U = floor01(min(250, w-0.5))
增重：L = ceil01(max(30, w+0.5))
      U = floor01(min(250, 1.2*w, 30*h*h))
维持：L = U = w
~~~

先判断 L<=U，再验证目标在 [L,U] 内。无解返回 422 TARGET_UNAVAILABLE，details.reasonCodes=['NO_FEASIBLE_TARGET']，allowedTargetRange=null，提示改选目标或结束，不显示一个无法满足的输入提示；有解但填错返回 VALIDATION_ERROR，并只给出由本人输入推导的合法目标区间。此区间不包含付费计算结果。

评审反例 170cm/110kg/减重现为 L=88、U=109.5，目标 90kg 可以通过目标规则；仍须通过完整输出守卫，不保证每个合法目标必然生成建议。对于如已处于目标上限仍选择增重的组合，明确“不支持该目标”，而非要求无休止改体重。

完整提交再次验证所有字段、同意、scope 和输出支持性，不依赖先前分步验证。本期只显示 BMI 数值，不输出诊断或分类标签。

BMI 定义是体重 kg 除以身高 m 的平方；CDC 的成人分类页面适用 20 岁及以上。本方案只采用该数值定义，不引入面向所有年龄的诊断标签。[CDC 官方说明](https://www.cdc.gov/bmi/adult-calculator/bmi-categories.html)

### 10.2 纯函数输入、输出与公式

函数签名设计：calculateAssessment(validatedInput, calculationDate, policy)，返回 SUPPORTED(result) 或 UNSUPPORTED(reasonCodes) 判别联合。policy 显式传入 demo-v1.1；不在函数内部访问 Date.now()。同输入、日期和算法版本必须产生相同结果。

~~~text
BMI = weightKg / (heightCm / 100)^2

静息能量估算 REE：
MALE   = 10 × weightKg + 6.25 × heightCm - 5 × age + 5
FEMALE = 10 × weightKg + 6.25 × heightCm - 5 × age - 161

活动系数（本演示映射）：
SEDENTARY = 1.20，LIGHT = 1.375，MODERATE = 1.55，HIGH = 1.725

maintenance = REE × 活动系数

减重：suggested = max(REE, maintenance - min(maintenance × 0.15, 500))
维持：suggested = maintenance
增重：suggested = maintenance + min(maintenance × 0.10, 250)
~~~

REE 采用 Mifflin–St Jeor 论文中的简化式；活动系数和目标调整比例是本方案明确选定的演示参数，并非从竞品反推，也不宣称是论文结论。REE 并不等同于针对个人的饮食处方，使用 max(REE,...) 也是计算策略，不代表自动满足医疗安全条件。[原始论文摘要与公式](https://pubmed.ncbi.nlm.nih.gov/2305711/)

计算中保留精度，先做输出守卫，再将最终热量 Math.round 为整数；BMI 显示一位小数、库内三位，展示按第 7.7 节避免双重舍入。不要先四舍五入 REE 再算 maintenance。

输出守卫属于本版演示策略：REE、maintenance、suggested 必须有限且 >0；未舍入 suggested 必须在 [1000,5000] kcal/day 内，否则返回 INTAKE_OUTSIDE_DEMO_RANGE，不生成报告、不插入结果、不展示该异常数值、不提供支付入口。该区间是演示支持窗口，尤其 5000 是产品上界，二者都不是个人的医学安全界线；不得通过 max/min 强行钳到边界后声称可用。NIDDK 工具明确提示低于 1000 的摄入问题，并排除孕哺人群，本方案借鉴其“拒绝不适用输出”的做法，不宣称复现其模型。[NIDDK 官方工具及限制](https://www.niddk.nih.gov/bwp)

分步执行位置：profile 检查年龄/确认；metrics 检查身体范围与目标可行域；activity 补齐后保存答案并计算 eligibility；submit 在事务中完整复核。UI 的不适用状态只带原因与退出/修正入口。既有会员的新测评不适用时，仍不生成该份报告，不能因为已付费绕过输出守卫。

必须保留的拒绝样例：女性 78 岁、120cm、30kg、维持、SEDENTARY，BMI≈20.833、REE=499、原始 suggested=598.8；新的预期不是显示 599 或钳到 1000，而是 UNSUPPORTED，结果表零新增，/pay 对该 DRAFT 拒绝。

### 10.3 预测日期与曲线

PDF 允许简单估算，本期采用显式的线性情景模型，不把复杂代谢动态作为两天交付前提：

~~~text
对于减重或增重：
weeklyChangeKg = 0.25
durationDays = ceil(abs(targetWeightKg - weightKg) / 0.25 × 7)
baseDate = 提交时服务器时间的 UTC 日期
targetDate = baseDate + durationDays 个日历日

对于维持：
weeklyChangeKg = 0
durationDays = 0
targetDate = baseDate
predictionStatus = AT_TARGET
~~~

0.25kg/周仅是产品情景参数；日期不宣称是摄入建议带来的科学因果预测。报告将其写成“按每周 0.25kg 的演示情景估算”，用户可看到假设。健康计划工具本身也需要明确适用范围与非医疗用途。[NIDDK 工具说明](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner)

曲线规则：起点为当前体重，之后按 7 天间隔线性插值；不足整周时补精确终点；同日期不重复；体重保留一位小数且不越过目标。维持目标仅返回一个起点，并显示维持状态。超过 730 天时设置 HORIZON_EXCEEDED，targetDate/durationDays 为 null、curve=[]，明确提示超出本模型时间窗口，不生成夸张日期。

示例校验：女性 30 岁，170cm，70kg，目标 65kg，MODERATE，baseDate=2026-09-28：BMI≈24.221，REE=1451.5，maintenance=2249.825，建议摄入=1912kcal/day，140 天，目标日期 2027-02-15。单测使用独立算出的固定值作为 oracle，不能调用被测函数生成期望值。

## 11. 权限、支付和缓存的闭环

结果访问分成两道独立判断：先确认资源属于当前用户，再判断此用户是否有有效订阅。会员身份不能授权读取其他用户的数据。

| 调用者 | 测评状态 | 订阅 | 响应 |
| --- | --- | --- | --- |
| 无凭证/凭证无效 | 任意 | 任意 | 401 |
| 其他用户 | 任意 | 即使有效 | 404 |
| 本人 | DRAFT | 任意 | 409 RESULT_NOT_READY |
| 本人 | COMPLETED | 未激活/已到期 | PREVIEW DTO |
| 本人 | COMPLETED | 当前有效 | FULL DTO |

实现两个显式转换函数 toPreviewDto 与 toFullDto，禁止使用对象展开复制 Prisma 全量模型再删除字段。检测范围包括 GET result、GET assessment、submit、pay、错误响应、RSC 页面数据和 HTML；权限不是前端隐藏效果。

结果、会话和订阅不进入共享应用缓存、CDN 缓存或静态页面预渲染。服务端每次查当前权益；浏览器仅缓存已经合法取得的数据并在支付、切换会话、页面恢复时重新读取。已经授权并下载的报告不能技术性收回，到期只限制后续请求。

Cookie 写请求要求 Origin 与固定 APP_ORIGIN 精确一致，使用 application/json；无 Cookie 的 Bearer 客户端通过凭证认证。创建 session 即使没有旧 Cookie，也必须检查 Origin。公开 demo 是固定资源只读 GET，无身份切换写入口；不能借它查询普通用户。Origin 取服务端配置，不信任客户端 Host 来决定允许域名。DELETE 本人数据同样必须做来源检查与本人授权。

部署前配置平台侧基础速率限制，覆盖创建会话和 /pay；具体能力与额度须在真实账户确认。不把单进程内存限流当作 Serverless 全局限流；共享限流若不可用，报告为线上防滥用能力限制，不以此伪造已验证结果。

| I03 | 跳步与重复 | 缺前置步骤 409；同 key 重试成功，revision 只增加一次 |
| I04 | 请求键复用 | 相同 key 不同 body 409，原数据不变 |
| I05 | 并发不同 key 同 revision | 用同步屏障从两个连接同时发起，恰好一个成功、另一个 409，无丢更新 |
| I06 | 并发同 key | 两个请求语义相同、数据只写一次，收到同业务回执 |
| I07 | Save 与 Submit 并发 | 结果基于合法版本快照；陈旧提交/保存冲突，不混入两份输入 |
| I08 | Submit 失败回滚 | 注入结果写入故障，测评不完成、无半条结果、无成功回执 |
| I09 | 重复 Submit | 同 key 回放；不同 key 对相同已完成测评只返回已有 resultId，不重算、不新增 |
| I10 | 未授权与跨用户 | 未登录 401，另一个有效会员拿他人结果仍 404 |
| I11 | 套餐状态篡改 | 随步骤上传 userId/subscriptionStatus/bmi 等字段被拒绝 |
| I12 | 免费数据泄漏 | 普通用户的所有 API/HTML/RSC 不泄漏付费字段；demo 只允许固定合成数据，不能混入普通测评 |
| I13 | 支付回放 | 一个 event、一次激活；同 event 不同本人测评为 409，未知套餐参数为 422 |
| I14 | 并发支付不同 event | 两个事件都记录，恰好一个 ACTIVATED、一个 ALREADY_ACTIVE；有效期不叠加 |
| I15 | 支付失败回滚 | 在订阅、会话、保留期、回执写入处分别注入故障；关联变更全部回滚 |
| I16 | 到期回放与新支付 | 旧 event 不重新激活；新 event 才开启新有效期 |
| I17 | 数据库约束 | 空库 migrate deploy，重复草稿/结果/事件违反预期唯一约束 |
| I18 | Cookie/Origin | 伪造来源写入被拒绝；同源 Cookie 与 Bearer 示例均能完成授权流程 |
| I19 | Demo 边界 | 普通用户进入/返回 demo 后身份和草稿不变，无 Set-Cookie；定位参数篡改拒绝，普通 API 不接受 demo ID 越权 |
| I20 | 不适用提交 | activity 可保存并返回 UNSUPPORTED；submit 422、结果零新增，/pay 409；付费用户同样不能绕过 |
| I21 | 会话与权益期 | 初始 7 天；激活后第 8/29 天仍 FULL，第 30 天 PREVIEW 且会话可访问；临近初始到期才支付仍覆盖新 30 天 |
| I22 | 无解与阶段目标 | 可行目标正常完成；无解返回 TARGET_UNAVAILABLE，不写错误整步，不出现重复输入死循环 |
| I23 | 未激活事件重放 | ALREADY_ACTIVE 的同 event/新 key 可回放；换测评冲突；到期后该旧 event 仍不激活，只有新 event 可以 |
| I24 | 模拟功能开关 | 默认关闭；pay/demo 返回 FEATURE_DISABLED 且零业务写入；关闭 pay 不影响已有有效权益读取 |
| I25 | 清理与支付竞争 | 清理行锁后复核期限，正在生效的会话/权益不得被清；仅过期且到 purge_after 才删除，排除 demo |
| I26 | 主动删除与越权 | 本人确认后七表依赖数据清除、旧 token 401；他人/只读示例不可删除；失败回滚、复制来源自引用也可同批删除 |
| I27 | 完整响应契约 | 所有成功/错误 DTO 通过响应 Schema；numeric/时间/null/arrays 一致，未知字段不泄漏 |
| I28 | 响应丢失后的恢复 | 支付提交成功后丢弃响应，客户端进入待确认；GET session 同步 Cookie，再 GET result，原键回放不延长期限 |

I09 业务幂等补充：submit 在回执判断后，如果资源已 COMPLETED，expectedRevision 只允许 source_revision 或当前完成 revision，返回已有结果标识；其他版本仍冲突。完整结果不得在此返回。这样不同 key 的重复点击不会重新计算，但明显过旧请求仍被拒绝。

### 13.3 Playwright 验收

1. 新浏览器会话进入首页，同意后填写 profile 和 goal。
2. 刷新、关闭标签页再打开；同一浏览器持久化 Cookie 的上下文恢复到 metrics。
3. 直接输入后续步骤 URL 被引导回服务端 nextStep。
4. 完成 metrics、activity、review，提交并看到免费 BMI 摘要。
5. 捕获所有业务响应及 HTML，断言没有完整预测和摄入结果。
6. 打开模拟支付弹窗完成解锁，确认完整 API 数据、图表和摄入量。
7. 再次刷新仍为会员；相同支付请求重放不会延长有效期。
8. 新无痕上下文访问同一个报告 URL 无权读取；已支付 /demo 可直接展示固定合成结果。
9. 普通用户填写一半进入 /demo 比较 preview/full，再返回，原 sessionId、草稿、权益和 Cookie 保持不变；同时覆盖已支付普通用户。
10. 不适用输出和无解目标展示明确说明及退出路径；不存在付费按钮；修正真实误填后可重新计算。
11. 模拟服务器已提交支付但响应被丢弃，页面显示待确认并重新查询；不能生成新事件重复执行，也不能误报未支付。
12. /privacy 二次确认删除；七表集成证据与浏览器旧身份失效对应。付费/演示功能关闭时，页面和 API 行为一致。

移动端 390×844 完整跑一条，桌面端 1440px 做页面可用性冒烟。断言来自接口与 DOM 语义，不把截图像素完全一致作为通过条件。

### 13.4 一键命令契约

以下脚本在实施时落实，当前尚不存在：

~~~shell
npm ci
npm run dev
npm run lint
npm run typecheck
npm run build
npm test
~~~

npm test 编排单元测试 → 独立 PostgreSQL 迁移 → HTTP 集成测试 → 启动生产构建测试服务 → Playwright。首次安装说明包括 Docker 与 Playwright Chromium 依赖；依赖不满足应明确失败，不能静默跳过集成/E2E后显示全绿。

提供 test:unit、test:integration、test:e2e 子命令。测试连接专用 TEST_DATABASE_URL，配置环境标识与库名双重防误连；不得向开发/生产库执行测试清空。端口和数据目录单独隔离，失败保存有限的脱敏 trace。

CI 属于加分项：有余量时使用 PostgreSQL service、锁定依赖、迁移后运行相同测试与生产构建，上传失败 trace。不以 Mock DB 通过替代真实事务测试；没有接入 CI 时仍必须本地一键运行并交付可复核结果。90% 分支覆盖仅为优化目标，不是硬性开工门槛，不能为了数字删减边界用例；是否交付以 R01–R13 和本版新增反例的行为证据为准。

时间相关测试使用可注入 Clock，数据库记录与 Cookie 均按同一测试时间构造，不真的等待 7/30 天。浏览器 Cookie 到期断言与后端伪时钟分开验证，防止测试时间与浏览器真实时钟错位导致假失败。故障注入只通过测试依赖实现，不向公网开放调试接口。

明确未覆盖：真实扣款与 webhook、临床有效性、跨设备账号找回、大规模负载、所有移动浏览器与异常断电。README 解释这些限制与本题范围的关系。

## 14. 部署、运维与交付

### 14.1 环境配置

| 配置 | 用途 | 是否可暴露给浏览器 |
| --- | --- | --- |
| DATABASE_URL | 应用运行连接 | 否 |
| DIRECT_URL | 迁移直连或会话池连接 | 否 |
| TEST_DATABASE_URL | 独立测试库 | 否 |
| APP_ORIGIN | 同源检查的可信基础地址 | 地址本身可公开，配置从服务端读取 |
| MOCK_PAYMENTS_ENABLED | 默认 false；独立挑战演示环境显式 true | 仅 capabilities 布尔值 |
| DEMO_MODE | 默认 false；显式开启公开合成数据入口 | 同上 |
| DEMO_PAID_SESSION_ID | 展示给评审的固定合成会话 ID | 是，非访问凭证 |
| DEMO_PAID_ASSESSMENT_ID | 固定示例报告定位；必须与 session 同属 is_demo 用户 | 是，非访问凭证 |
| APP_ENV | local/test/demo/production；隔离测试与公开演示 | 可公开环境标签，不公开密钥 |

运行请求使用池化连接；迁移使用支持迁移的直连或 session pooler。Supabase 对 Serverless 建议准备 transaction pooler，Prisma 配置方式必须按最终锁定版本核对；不混用不同主版本的 schema/config 示例。[Supabase Prisma 集成文档](https://supabase.com/docs/guides/database/prisma)

数据库和 Web 部署选择相近区域；连接池大小受 Supabase 连接额度约束。生产启动不执行迁移，部署流水线先 migrate deploy 再放行新版本。

环境校验在启动时执行：缺少必要地址/密钥、Origin 含路径、测试库与演示库重复时明确失败；布尔开关只接受明确的 true/false，缺省关闭。APP_ENV=production 时禁止开启 MOCK_PAYMENTS_ENABLED/DEMO_MODE，挑战公网应用使用独立 APP_ENV=demo 与醒目模拟标识。每个预览部署使用自己的 APP_ORIGIN，不允许通配域名；测试库不连接公开演示服务。数据访问角色和迁移角色的权限在首日连接测试中分别验证。

### 14.2 演示会话

种子脚本创建固定 user/session/assessment/result/subscription 的合成示例。示例 session 的 token 仅在生成时用于哈希后立即丢弃，不保存环境变量、不发给浏览器；普通认证服务直接拒绝 is_demo=true 身份。sessionId 只用于交付标识，不用于登录。

GET /api/v1/demo/paid 从服务端配置读取两个固定 ID，检查 session 与 assessment 同属 is_demo=true 用户、session 未撤销且未过期、测评 COMPLETED、结果存在、订阅有效，才能调用专用公开示例 Presenter。只接受 view=preview/full；拒绝额外 userId/sessionId/assessmentId 等定位参数。该端点忽略普通身份进行固定样例读取、不写 Cookie；普通结果接口仍执行所有权鉴权。

README 提供实际已支付 sessionId、/demo URL、预期 FULL 字段，满足评审直接对比要求。任何人可以访问这个专门的公开合成示例，这是演示功能，不开放任意 sessionId 登录。

演示会话与订阅都有有效期，seed 使两者至少覆盖交付后 30 天，并显示实际到期时间；到期/缺记录返回 DEMO_NOT_READY，不能假装已支付。维护者显式重新设定示例权益/会话期限，保留原结果快照，不提供公网续期管理接口。普通用户需自行走 /pay，以验证真实业务路径。demo 显示“返回我的测评”，仅导航回首页，不改变普通 Cookie。

### 14.3 日志与故障定位

结构化记录 requestId、路由、脱敏资源标识、耗时、HTTP 状态、错误码、是否幂等回放。健康回答、完整报告、Cookie、Authorization、环境变量和 SQL 连接串不进入普通日志。

必要事件：session.created、assessment.step_saved、assessment.revision_conflict、assessment.unsupported、assessment.completed、payment.activated、payment.already_active、payment.replayed、user.deleted、retention.cleaned。日志只带白名单原因码、脱敏标识与统计，不包含删除数据副本。线上请求失败，用户可提供 requestId 供维护者查日志。

监控检查：/api/health 存活、/api/ready 数据库就绪、关键 API 错误比例、保存/提交耗时。性能验收采用少量实测记录 warm/cold 请求，不在未压测前承诺固定延迟或并发数。

### 14.4 部署验收与回退

1. 空库迁移、合成 seed；先确认 Web 连接数据库正常。
2. 本地 lint、类型检查、构建及核心测试全部通过；接入 CI 时要求同样通过。
3. 部署后无痕窗口走一次完整漏斗；每个请求核对业务状态而非只看 HTTP 200。

5. README 从启动到支付的命令由另一全新会话重放，不能只附未经运行的示例。
6. 保留前一个可用 Web 版本；初期数据库迁移采用加法变更，发现问题先回退应用或向前修复，不自动删除表/列。

目前尚未确认可用的 Vercel/Supabase/GitHub 部署账号、公网访问区域和 CI 权限；设计与本地实现可以先推进，实际发布需使用用户授权的资源。方案设计本身不创建外部项目、不发邮件。
